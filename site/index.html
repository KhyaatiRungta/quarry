Sandboxed data analyst agent

Ask your data a question and get back a number that was actually computed.

Quarry writes pandas or SQL, runs it in a sandboxed subprocess, reads the real traceback when it fails, fixes its own code, and refuses to report a figure that never came out of an execution.

Three things it does that matter

A code interpreter makes an analyst agent honest. It also makes it dangerous and fragile. These are the parts that deal with that.

Runs code, not guesses

The generated code executes in a subprocess against the real dataframe, and the real stdout, result and duration come back as the next message.

Ask for a mean over a column stored as "18.3 C" and you get a number that survived a type error, not a plausible sentence.

Recovers from its own errors

Failures are classified and the real traceback goes back verbatim, so a wrong column name costs one extra step instead of ending the run.

The repair loop is a single flag, so the benchmark can measure exactly what it buys and what it costs.

Proves where the number came from

Every answer must declare the values it rests on, and each one is matched against the text the sandbox actually produced.

A figure that was never computed does not get out; it is sent back, and if the model insists the answer is returned flagged.

How it works

A hand-written ReAct loop, under 400 lines including the trace writer. No agent framework: the loop is the part worth reading. The red edges below are the two correction paths.

01

The CSV is read as-is. Nothing is cleaned or coerced, because coercing here would hide exactly the failures the loop exists to handle.

02

Columns, dtypes, null counts, cardinality and three sample rows go into the system prompt, so the model starts grounded instead of guessing.

03

Generated code is parsed into an AST and walked before anything executes. A rejection returns the specific rule broken plus the allowlist.

04

Code that passes runs in a fresh subprocess with its own working directory, a hand-built environment holding no credentials, and a 30 second timeout.

05

stdout, the result repr and type, the traceback and the duration become the next message. Tracebacks are truncated from the front, where the useless frames are.

06

Every value in the final answer is matched against real execution output, allowing honest rounding and percent conversion but nothing else.

How the task set is graded

43 tasks over three bundled datasets. 33 are graded numerically against expected values computed by a separate reference implementation in scripts/build_tasks.py, 7 against a string predicate, and 3 genuinely open-ended ones by an LLM judge against a written rubric. Which grader ran is recorded per task in results/RESULTS.md. Ground truth is never typed by hand and never produced by the agent under test.

Design decisions

Each one is a tradeoff, so each one lists what it cost.

A subprocess, not exec in the agent process
Generated code runs via subprocess.Popen in its own session, its own working directory and a hand-built environment that does not contain the API key. Why: in-process execution means a runaway loop hangs the agent, a segfault in a C extension takes the whole run down, and generated code can reach the agent's own globals including credentials. A timeout you cannot enforce is not a timeout. What it cost: about 1.5 to 2 seconds of interpreter and pandas import time per execution, which dominates the latency numbers above, and the dataframe has to be pickled to disk and read back on every call.
AST allowlisting, not regex blocklisting
The guard parses the code and walks it. Imports are checked at the node level, forbidden names and dunder attribute access are checked wherever they appear, and open is permitted only with a literal filename inside the run directory in a read mode. Why: a regex for import os misses import os, from os import system and import os.path as p, and fires on the string "import os" inside a comment. The AST collapses all of those into one rule, and returns a precise message the model can act on rather than a flat refusal. What it cost: the allowlist rejects legitimate code, for example anything needing scipy or sklearn, and it must be widened by hand. It also cannot see through df.query and pd.eval, which evaluate expression strings inside pandas after the guard has finished.
A mechanical verify gate rather than a second model opinion
final_answer requires the values the answer rests on, and each one is matched against the text the sandbox actually produced during the run, allowing an honest rounding or a percent/proportion conversion but nothing else. Why: the failure this catches is an answer that reads perfectly and contains a number that was never computed. A judge model cannot catch that, because it has the same blind spot. String and numeric matching against real output can, it costs no tokens, and it is checkable by a reader. What it cost: it is a groundedness check, not a correctness check. A number that was genuinely computed by wrong code passes. Values the model paraphrases instead of quoting can trip it, which shows up as a retry.
Bounded steps, bounded repairs, bounded spend
max_steps=8, a repair budget of 4, and a $0.50 per-run cost ceiling checked after every model turn. Why: the characteristic failure of a repair loop is not one bad answer, it is twenty turns of a model rewriting the same broken line while the bill runs. A bound turns an unbounded cost into a reported stop_reason. What it cost: genuinely hard multi-step questions can hit the ceiling and return nothing. That shows up as a failure in the results table, which is the correct place for it.
Ground truth computed by a reference implementation, not written by hand
Every expected value in tasks.jsonl is produced by plain pandas in scripts/build_tasks.py, and 33 of the 43 tasks are graded numerically against it. Why: hand-typed expected values drift from the data and quietly become wrong, and grading everything with an LLM judge means the thing under test is also the ruler. What it cost: only questions with a single checkable value can be graded this way. Three genuinely open-ended tasks still need a judge, and they are labelled as judged wherever they appear.

Limitations

Specific, and not softened. This is the section to read before trusting anything above it.

  • The sandbox is not a security boundary. It is defence in depth against a confused model, not containment of an adversarial one. Code that passes the guard runs as your user with your filesystem and your network. There is no syscall filtering, no namespace isolation, and on macOS no enforced memory cap, because RLIMIT_AS is not honoured there for the mappings numpy and pandas make; the cap is applied on Linux only and the code says so. Network access is not blocked at all: the allowlist keeps socket and requests out of the import list, which stops an absent-minded model, not a determined one. Run it in a container if the model output is not trusted.
  • Known holes in the guard. df.query() and pd.eval() evaluate expression strings inside pandas, after the AST walk is over. C extensions can be reached through allowed modules. Resource exhaustion below the caps, filling the run directory to the 64 MB file-size limit, is possible.
  • One table at a time. There is no multi-table join, no schema discovery across files, no foreign keys. The tasks tagged join are self-joins within a single table. Real analytical work is mostly joins, so this is the largest functional gap.
  • No memory between questions. Every ask starts from an empty message list. You cannot say "now break that down by month", which is how people actually use an analyst.
  • The LLM judge is fallible and is used for three tasks. It grades the open-ended items against a written rubric with a single sampled verdict, no second opinion and no inter-rater check. Those three tasks are marked judge in the task file, in RESULTS.md and in the results JSON, and the judge is skipped entirely offline.
  • Charting is matplotlib only, and unevaluated. One PNG per run, no interactivity, and no grading of whether the chart was the right chart. A run can produce a technically valid and completely useless figure and nothing here notices.
  • The datasets are synthetic. They are seeded generators in scripts/make_data.py, built to contain specific messes: text-typed numerics, unit suffixes, sentinel nulls, inconsistent casing, mixed timestamp formats. They are not a sample of real-world data, so the task success rate is a measurement on this suite and should not be read as a general capability number.
  • Single-model, single-sample. Each task is run once per arm, so the difference between the arms carries sampling noise that is not quantified here. No variance across seeds, no comparison across models.

Running it locally

Python 3.11, a virtualenv, and a requirements.txt. No build step, no Docker, no accounts.

shell
$ python3.11 -m venv .venv && source .venv/bin/activate
$ pip install -r requirements.txt

# offline: replays recorded model turns, really executes the code
$ python -m quarry ask --offline --data data/sales.csv \
    "Which region has the highest total revenue, and by how much does it beat the runner-up?"

# render any run to a standalone page
$ python -m quarry view runs/example/trace.json --out site/trace.html

# the tests pass with no API key
$ pytest

# live, against OpenRouter
$ export OPENROUTER_API_KEY=sk-or-...        # or put it in .env
$ export QUARRY_MODEL=anthropic/claude-3.5-sonnet
$ python -m quarry ask --data data/sensors.csv "What is the mean temperature?"

# the benchmark, both arms, writes results/
$ python -m quarry bench
$ python -m quarry bench --limit 5 -v
$ python -m quarry bench --offline

The code, the task set, the traces and the results file are all in the repository. The offline demo runs without a key.
